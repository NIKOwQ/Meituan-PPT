## Slide 2 · 痛点 + 方案 + 定位

### Primary

传统人工评测：耗时长、覆盖低、归因难

### Secondary

**三张痛点卡片：**

| 卡片 | 标题 | 正文 |
|------|------|------|
| 1 | 耗时长 | 质检员逐条听录音、人工打分，一条指令对应上百条通话录音。传统质检需要数小时才能完成一条指令的评估。 |
| 2 | 覆盖低 | 人工抽检覆盖率不到 1%，绝大多数对话没有被检查。漏掉的对话里可能藏着 Agent 最严重的违规。 |
| 3 | 归因难 | 知道 Agent 有问题，但说不清是哪条指令写错了。无法指导运营"改哪句话能让 Agent 表现变好"。 |

**方案区（高亮条）：**

> **我们的方案：** 输入一条外呼指令，系统自动模拟多轮对话，逐条测试 Agent 是否遵守了指令里的各类约束，输出一份逐约束诊断报告。不是给一个总分，而是告诉运营"你的 Agent 在'安慰挂断'这条约束上只有 47% 的通过率，改一下指令措辞能到 85%"。

**定位：**

> 我们调研了 7 个商业平台（阿里云 SCA、沃丰、讯飞等）和 5 个学术框架。他们全在做**事后质检**——听已有的录音，判断合规性。
> 我们做的是**事前测试**——主动生成测试对话，暴露 Agent 的弱点，告诉运营怎么改。

### Tertiary（点击"竞品对比"展开）

| 维度 | 传统质检平台 | 学术评测框架 | **我们** |
|------|------|------|------|
| 测试对象 | 已有的人类通话录音 | 人工构造的测试用例 | **AI Agent 的行为（主动模拟测试）** |
| 覆盖率 | 抽检 < 1% | 取决于用例数量 | **每条约束至少测 N 次，覆盖率可量化** |
| 输出形式 | 合规 / 不合规 | 评分 | **逐约束通过率 + "改哪句话能好"** |
| 场景适配 | 换场景要重新配置 | 换场景要重写用例 | **换指令不需要改代码** |
| 归因能力 | 无 | 弱 | **逐约束归因到指令原文** |

## Slide 4 · V4 核心机制

### Primary

不预解析了。直接从原文选约束来测。

### Secondary

**数据流：** 原始指令 → User LLM（选约束 + 生成用户消息）→ 双重门控（代码 + LLM 验证）→ Agent 回复 → LLM 评估

**三张卡片：**

| 卡片 | 标题 | 正文 |
|------|------|------|
| 1 | 不需要结构化 | 不需要先把指令解析成流程图或结构化格式。User LLM 直接从原始长指令里选一段约束文本，生成一句自然用户消息去触发。换了不同领域的指令，不需要改代码就能跑。 |
| 2 | 覆盖率可量化 | 精确到字符位置。把原始指令展开为字符序列，标记哪些属于约束文本、哪些是结构（标题、编号）。结构性文本自动排除。覆盖率 = 已测试约束字符 / 有效约束字符总数。纯函数计算，不依赖 LLM。 |
| 3 | 逐约束归因 | 每条约束独立计算通过率，哪条约束 Agent 表现差，单独标红。不报总分。运营看到红色就知道该改哪句话，看到绿色就知道不用动。 |

### Tertiary（点击卡片展开）

**卡片 1 展开：**

> 传统做法是先把指令解析成结构化格式（流程图、决策树），然后沿着图路径测试。但长指令本身就是欠规格化的——步骤是线性描述的，隐含了分支和终止条件。解析这一步本身就是不稳定的。
> V4 的创新在于：跳过解析，直接测。User LLM 从原文选约束，不预设指令格式。

**卡片 2 展开：**

> 举例：一条 2000 字的骑手外呼指令，其中约 800 字是约束文本（"告知骑手合同已生效""越界问题固定话术""坚持无法配送要安慰挂断"等），其余 1200 字是结构性描述（标题、编号、分段标记）。
> 覆盖率 = 已测试的那 800 字中覆盖了多少。不是按"约束条数"算，而是按"字符位置"算，更精确。

**卡片 3 展开：**

> 和直接用 GPT 打分的区别：GPT 给一个数字（73 分），运营不知道该改什么。我们给逐约束通过率（"安慰挂断 47%"），运营秒懂该改哪句话。每个评判有完整证据链（用户消息、Agent 回复、评判理由），可审计。

## Slide 7 · 架构总览

### Primary

V4Collector — 循环批次，并行对话，覆盖率驱动退出

### Secondary

**核心编排流程：**

```
原始指令 → 清洗为单行文本 → 循环批次：
  每批 N 组并行对话（ThreadPoolExecutor）
  每组对话：
    Agent 开场白 → 循环：
      User LLM 从原文选约束 + 生成用户消息
      → 双重门控验证
      → Agent 回复
      → 收束为 Segment（一个测试片段）
  → 合并所有组结果 → 计算覆盖率 → 覆盖率达标？退出 : 继续
→ 对每个 Segment 做 LLM 评估（Agent 是否遵守约束）
→ 输出 V4DatasetReport（覆盖率 + 逐约束评估 + 证据链）
```

**并行工位：** C0 / C1 / C2 / C3 — 每个工位独立运行一组对话，互不干扰

**覆盖率退出逻辑：** 覆盖率 < 目标 → 继续下一批 → 达标 → 退出循环

### Tertiary（点击展开批次策略）

> 覆盖率达标后，选题策略自动切换：
> **前半数组**：强制从"未充分测试的约束"中选题，针对性补齐短板
> **后半数组**：继续自由发现，避免遗漏
>
> 三路 Prompt 选择逻辑：
> 1. 自由发现 — 覆盖率低时，让 User LLM 自由选择约束
> 2. 定向补充 — 覆盖率过半后，强制补弱约束
> 3. 多轮承接 — 同一约束跨轮追问，测不同失败模式

## Slide 8 · 架构细节（5 个 tab）

### Primary

关键机制详解（点击标签切换）

### 默认展示：双重门控

**① 双重门控 — 代码 + LLM 串联拦截**

> **代码门控**（100% 确定性）：
> - 子串匹配：验证约束文本是否出现在用户消息中。如果 User LLM 选了"安慰挂断"这条约束，但生成的用户消息里完全没有相关表述，直接拦截。
> - 去重：防止重复测试同一约束的同一触发方式。
> - 格式校验：用户消息长度、特殊字符等基本检查。
> - 优势：不通过直接拦截，不消耗 LLM 调用，零成本。
>
> **LLM 门控**（语义层）：
> - 验证用户消息是否在语义上适配所选约束。
> - 比如 User LLM 选了"测试语气自然"，但发了一句"你的合同已生效"——语义上不对，拦截。
>
> 两道门串联，只有同时通过才交给 Agent。实测拦截了约 30% 的无效测试。
>
> 流程：用户消息 → 代码门控 → LLM 门控 → 通过 → Agent

**② 字符位覆盖率 — 精确到字符位置**

> 把原始指令展开为字符序列，标记每个字符属于"约束文本"还是"结构文本"（标题、编号、分段标记）。结构文本自动排除。
>
> **覆盖率 = 已测试约束字符 / 有效约束字符总数**
>
> 每条约束至少被测试 N 次（可配置）才视为"充分测试"。
>
> 纯函数计算，不依赖 LLM，结果完全确定性、可复现。关键指标不受 LLM 随机性影响。

**③ 定向补充 — 覆盖率过半后加速补弱**

> 覆盖率 ≥ 目标阈值后，User LLM 的选题策略自动切换：
> - 前半数组：强制从**未充分测试的约束**中选题，针对性补齐
> - 后半数组：继续自由发现，避免遗漏未被识别的约束
>
> 实测对比：
> - 无定向补充：20+ 批才达标
> - 有定向补充：7 批达标
> - 收敛速度差 **3 倍**

**④ 多轮状态机 — none → need → continue → done**

> 一条约束可以在同一对话里跨多轮持续测试，而不是只触发一次。
>
> 状态流转：
> - none → 还没触发这条约束
> - need → 刚触发了，等 Agent 回复
> - continue → 继续追问，测更深层的失败模式
> - done → 测试完毕，换下一条约束
>
> 举例："坚持无法配送"可以测：
> - 用户第一次说"我送不了" → Agent 怎么回
> - 用户坚持说"我真的没法配送" → Agent 怎么回
> - 用户情绪激动说"别再劝我了" → Agent 怎么回
> 三种情境，三种失败可能性，一条约束测透。

**⑤ 代码结构 — 6 个模块 ~2000 行**

> | 模块 | 职责 |
> |------|------|
> | models.py | 10 个 Pydantic 数据模型（Segment、Turn、Eval、Report 等） |
> | prompts.py | 8 个 Prompt 模板（选约束 / 生成消息 / 门控 / 评估等） |
> | coverage.py | 覆盖率计算，纯函数无 LLM 依赖 |
> | collector.py | 核心编排循环（批次调度 + 对话管理） |
> | render.py | 终端报告渲染 + JSON 持久化 |
> | run_v4_dataset.py | CLI 入口（argparse，支持参数配置） |
>
> 前端：FastAPI + SSE 实时推送，纯 HTML/CSS/JS，无框架依赖。

## Slide 9 · 迭代故事

### Primary

10 天 4 次迭代，每次都是数据逼我们改的

### Secondary

**左列 · V2 的失败（视觉冲击）：**

> 7 张不同的 SVG 流程图并排
>
> V2 的做法：让 LLM 一次性生成完整流程图，并行 3 次投票合并。
> 结果：rider 指令连续跑了 7 次，7 种完全不同的图结构，没有两次同构。
>
> **这意味着什么？** 测量工具本身不稳定，下游测到的不只是 Agent 能力，而是 parser、agent、judge 三个随机组件的联合输出。你没法把结果归因到被测对象上。

**右列 · 从 V3 到 V4：**

> V3 把"一次生成完整图"拆成 4 步（抽节点 → 抽边 → 逐边投票校验 → 组装），6/6 拓扑一致。
>
> 但很快发现：图稳定了 ≠ 问题解决了。字数控制、语气、超范围处理——这些约束的测试依然不稳定。更根本的是：长指令本身就是欠规格化的，你让 LLM 解析成唯一的图，它做不到。
>
> V4 决定：不解析了。直接从原文选约束来测。每次推倒都不是拍脑袋，是数据逼我们改的。

### Tertiary（点击展开完整迭代对比表）

| | V1 | V2 | V3 | V4 |
|---|---|---|---|---|
| 方法 | TestPoint 理论 | LLM 一次生成流程图 | 原子拆分 4 步校验 | 不解析，直接从原文测 |
| 稳定性 | 不适用 | 0/7（7 次全部不同） | 6/6（全部一致） | 不依赖图结构 |
| 覆盖维度 | 单条路径 | 流程路径 | 流程路径 | 全约束（字符位） |
| 归因粒度 | 无 | 按路径 | 按路径 | 逐约束 |
| 泛化能力 | 弱 | 弱 | 弱 | **零代码适配** |
| 推翻原因 | — | 不稳定 | 约束拆解不稳定 | — |

## 设计规范

### 三层信息的视觉规则

| 层级 | 字号 | 颜色 | 位置 | 交互 |
|------|------|------|------|------|
| Primary | 48-72px | text-1（最深） | 页面顶部/居中 | 始终可见 |
| Secondary | 14-22px | text-2（中等） | Primary 下方 | 始终可见 |
| Tertiary | 13-14px | text-3（较淡） | 底部或可展开区域 | 点击展开/收起 |

### Tertiary 展开方式

- **竞品对比表**（slide 2）：点击 pill 标签展开
- **证据链 case**（slide 3、5）：点击红色行展开
- **卡片详情**（slide 4）：点击卡片展开
- **为什么能泛化**（slide 6）：点击展开文字块
- **批次策略**（slide 7）：点击展开文字块
- **技术 tab**（slide 8）：5 个 tab 切换（已有交互）
- **迭代对比表**（slide 9）：点击展开表格
- **技术栈**（slide 10）：点击展开文字块
- **JSON 记录**（slide 11）：点击展开代码块

### 主题配色

右下角 4 个圆点切换：美团黄 / 多巴胺 / 暗夜 / 樱花。每套主题覆盖背景、文字、阴影、渐变等全部视觉属性。
