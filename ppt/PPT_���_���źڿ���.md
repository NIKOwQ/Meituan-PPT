## P2 · 痛点 + 方案 + 定位（90 秒）

这页三件事，快过。

**痛点**：命题方原话——"传统人工评测：耗时长、覆盖低、归因难"。质检员一天听几百条录音，只能抽检不到 1%，知道有问题但说不清怎么改。

**方案**：输入一条外呼指令，系统自动模拟多轮对话，测试 Agent 是否遵守了指令里的各类约束，输出逐约束诊断报告。

**定位**：我们调研了阿里云 SCA、沃丰、讯飞这些平台——全在做"事后质检人的行为"。我们做的是"事前测试 AI Agent 的行为"。他们告诉运营"这通电话合规吗"，我们告诉运营"你的 Agent 哪里不行、怎么改"。

这三句话就是评委需要知道的全部定位信息。不展开，后面全用 Demo 说话。

## P3 · V2 那天晚上（90 秒）

这一页讲故事，不讲故事板。

我们用 LLM 一次性生成流程图，并行 3 次投票合并，看起来挺合理。管线跑通了。

然后我们拿 rider 指令连续跑了 7 次。

（展示这张表，停留 10 秒，别急着翻）

| 运行 | 节点 | 拓扑 |
|------|------|------|
| 1 | 5 | A→B→C→E, B→D→E |
| 2 | 5 | A→B→C→D→E, B→D |
| 3 | 5 | A→B→C→D→E |
| 4 | 5 | A→B, A→C→D, E 孤立 |
| 5 | 5 | A→B→C, B→D→E |
| 6 | 6 | A→B→C, B→D→E, F 孤立 |
| 7 | 5 | A→B→C→D→E, D→E |

7 次，7 种完全不同的图。没有两次是同构的。

这意味着什么？下游测到的不只是 Agent 能力，而是 parser、agent、judge 三个随机组件的联合输出。测量工具本身不稳定，你没法把结果归因到被测对象上。

我们没法假装这个问题不存在。所以管线推倒重来。

（翻页要快，制造节奏感）

## P4 · 原子拆分：从 0/7 到 6/6（90 秒）

V3 做了一件事：把"让 LLM 一次生成完整图"拆成了 4 步——先抽节点，再抽边，逐条边投票校验，最后组装。每一步的模糊空间都被压到了最小。

结果：rider 指令连续 6 次，拓扑完全一致，0 个 block。

| 指标 | V2（7 次） | V3（6 次） |
|------|-----------|-----------|
| 拓扑一致 | 0/7 | 6/6 |
| Block 诊断 | 43% | 0% |
| 歧义数 | 5-9 | 0 |

但这张表不是重点。重点是接下来发生的事。

---

## P5 · V3 解决了图，但没解决根本问题（60 秒）

V3 让流程图稳定了。但我们很快发现：流程遵循只是 Agent 能力的一部分。字数控制、语气、超范围处理、挽留策略——这些约束的测试，V3 做不好。约束拆解本身也不稳定。

然后我们意识到一个更根本的事：长指令本身就是欠规格化的。步骤是线性描述的，但隐含了分支和终止条件。你让 LLM 把它解析成唯一的图，它做不到不是因为 LLM 差，是因为输入本身就不确定。

所以 V4 我们做了一个决定：不解析了。

---

## P6 · V4：不预解析，直接测（60 秒）

V4 的做法：User LLM 直接从原始长指令里选一段约束文本，生成一句自然用户消息去触发，通过双重门控验证后交给 Agent，最后评估 Agent 是否遵守。

不需要结构化指令，不需要生成流程图。换了不同领域的指令，不需要改代码就能跑。每条约束单独归因，覆盖率可量化。

从 V1 到 V4，每次推倒都不是拍脑袋，是数据逼我们改的。V2 跑出 7 种图，所以拆原子。V3 约束拆解不稳定，所以不解析。V4 是被逼出来的，不是设计出来的。

## P7 · V4 架构，一页（60 秒）

```
原始指令 → 清洗为单行 → 循环批次：
  每批 N 组并行对话（ThreadPoolExecutor）
  每组对话：
    Agent 开场白 → 循环：
      User LLM 选约束 + 生成用户消息
      → 代码门控（拦截格式错误和重复）
      → LLM 门控（验证语义匹配）
      → Agent 回复
      → 收束为 Segment
  → 合并结果 → 覆盖率 → 退出检查
→ 对每个 Segment 做 LLM 评估
→ 输出报告
```

一句话：User LLM 从原文选约束，双重门控拦截无效测试，评估每个 Segment Agent 是否通过。覆盖率可量化，每条约束可归因。

细节（三路 Prompt、字符位覆盖率、定向补充、多轮状态机）留在答辩环节展开。评委问什么说什么，不问不讲。

## P10 · 报告解读（30 秒）

评测跑完后展示报告：

```
逐约束评估明细:
  约束                           片段  通过  失败  通过率
  告知骑手合同已生效...              8     8     0    100%
  越界问题固定话术...               12    11    1     92%
  保持语气自然                      7     7     0    100%
  坚持无法配送→安慰挂断              15    7     8     47%
```

让 47% 那行红色自己说话。不要提前剧透，让观众自己看到那个红色。

然后说一句："Agent 在 15 次测试里只有 7 次做到安慰后挂断，其余 8 次都在继续挽留。系统自动把它标红了。"

不解释什么是覆盖率、什么是 segment。评委看到那行红色的瞬间就懂了。

## P11 · Before/After 闭环（60 秒）

这一页回应"然后呢"这个追问。

左边（Before）：当前指令里写的是"尽量挽留不想配送的骑手"。Agent 理解成"尽量挽留"，所以即使用户坚持了它还在挽留。通过率 47%。

右边（After）：把指令改成"如果骑手坚持确实无法配送，必须停止挽留，安慰后挂断"。重新评测。

（展示结果：同一约束通过率从 47% 提升到 85%+）

一条指令改动，通过率从 47% 到 85%。不是我们改了代码，是系统告诉运营"改这句话"，运营改了，就好了。

这就是闭环。测出来问题，定位到原因，给出建议，改完验证。不是只出报告就完了。

如果 Before/After 的数据还没跑出来，可以做一版模拟的。但要标注清楚。

## P12 · 收尾（30 秒）

回到命题方的三个痛点：

耗时长——一条指令进去，几分钟出报告。
覆盖低——每条约束至少测 N 次，从抽检变成全检。
归因难——逐约束通过率加完整证据链，告诉运营改哪句话能好。

最后一句话：传统质检告诉运营"这通电话合规吗"。我们告诉运营"你的 Agent 哪里不行、怎么改"。

## P13 · 答辩弹药库（不主动展示，评委问到才用）

### "和人工标注的一致性是多少？"
不主动提。如果被问，说"目前还没做完整的校准实验"。然后立刻翻到报告里的两个具体 case，把 User 消息、Agent 回复、评判证据摆出来，让评委自己判断 LLM 判得对不对。证据链摆出来比报 kappa 系数有用。

### "和直接用 GPT 打分有什么区别？"
GPT 给一个数字。我们给诊断。逐约束标注，按约束统计通过率，定位最薄弱环节，每个评判有完整证据链。GPT 告诉你 73 分，我们告诉你哪条约束不过、为什么不过、怎么改。

### "加一个新场景要多久？"
不需要改代码。我们验证了两条完全不同领域的指令——骑手外呼和商家直播升级——同一套管线直接跑。如果评委现场给了新指令，能跑就当场跑。

### "LLM 评测本身不稳定怎么办？"
代码门控是 100% 确定性的（子串匹配、去重），只有语义判断走 LLM。覆盖率计算是纯函数，不依赖 LLM。关键指标不受 LLM 随机性影响。

### "能处理多少并发？"
目前单进程加 ThreadPoolExecutor。核心逻辑无状态，水平扩展没有技术障碍。

### 技术细节储备（评委深挖时展开）
- 三路 Prompt 选择逻辑：自由发现 / 定向补充 / 多轮承接
- 字符位覆盖率：精确到字符位置的覆盖率计算，结构性文本自动排除
- 定向补充策略：覆盖率过半后前半批强制补弱约束，7 批达标 vs 20+ 批
- 多轮约束状态机：none → need → continue → done
- 代码拆分：6 个文件，覆盖率计算纯函数无 LLM 依赖，1532 行单文件拆成 4 个模块
